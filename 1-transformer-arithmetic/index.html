transformer arithmetic & resource estimation

overview

understanding the computational and memory requirements of transformer models is essential for training llms efficiently, sizing gpu clusters, estimating training time, estimating inference latency and throughput, and provisioning inference infrastructure.

model computations are typically expressed in FLOPs (floating point operations). hardware accelerators like gpus specify their compute capacity in FLOPs/s (floating point operations per second). peak compute throughput varies significantly across data types, where lower-bit precision formats (such as FP8, INT8, or FP4) deliver higher tensor-core throughput than standard FP16 or BF16, which in-turn deliver higher throughput than FP32.

numerical data types in deep learning

floating-point representations determine how numbers are stored in memory and processed by hardware accelerators. understanding the bit-level anatomy of data types is critical for balancing memory footprint against numerical stability.

bit-level breakdown

  • float32 (32-bit = 4 bytes): 1 sign + 8 exponent + 23 fraction
  • float16 (16-bit = 2 bytes): 1 sign + 5 exponent + 10 fraction
  • bfloat16 (16-bit = 2 bytes): 1 sign + 8 exponent + 7 fraction
  • fp8_e4m3 (8-bit = 1 byte): 1 sign + 4 exponent + 3 fraction
  • fp8_e5m2 (8-bit = 1 byte): 1 sign + 5 exponent + 2 fraction

newer hardware architectures, such as nvidia h100 gpus, introduce 8-bit floating-point formats.

anatomy of a floating-point number

the general mathematical value of a floating-point number is expressed as:

$$\text{value} = (-1)^S \times \left(1 + \frac{M}{2^m}\right) \times 2^{E - \text{bias}}$$

where the fractional term $\left(1 + \frac{M}{2^m}\right)$ ranges from $1$ (inclusive) to $2$ (exclusive).

range vs. precision trade-off

  • exponent ($E$): determines the dynamic range (how high or low $2^x$ can go). having a high range for the exponent allows us to represent smaller numbers better and prevents underflow.
  • fraction / mantissa ($M$): determines the precision or resolution (the granularity between representable numbers).

bfloat16 shares the same 8-bit exponent width as float32, giving it an identical dynamic range (making training numerically stable without frequent underflows), albeit at a lower precision due to the 7-bit mantissa.

inspecting numerical properties in python can be done via torch.finfo(torch.float32).

mixed precision training & data type roles

  • 16-bit data types are generally sufficient for feed-forward computations.
  • however, training operations such as storing optimizer states (e.g., AdamW momentum/variance) and accumulating gradient values require 32-bit precision to prevent catastrophic cancellation and rounding errors.
  • mixed precision training bridges this gap by executing forward and backward passes in 16-bit while maintaining master weights and optimizer updates in float32.

intuition on FP32 vs. BF16 in mixed precision training

think of bfloat16 as something which is transitory. forward-pass values which are computed and used once are fine in bf16. but values that are being accumulated over time—such as gradient updates—must be maintained in float32.

counting parameters and flops: linear projection

with the numerical data types established, we now turn to resource estimation. as our first building block, we examine a standard linear projection (matrix multiplication).

setup

consider an input matrix $X$ of shape $(\text{bs} \times d_1)$, where $\text{bs}$ represents the batch size (or number of tokens) and $d_1$ is the input feature dimension. we project this input through a weight matrix $W$ of size $(d_1 \times d_2)$ to produce an output matrix $Y = X @ W$ of shape $(\text{bs} \times d_2)$ (ignoring bias for simplicity).

number of parameters

the learnable parameters of the linear layer reside entirely within the weight matrix $W$. since $W$ has dimensions $d_1 \times d_2$, the total parameter count is:

$$\text{parameters} = d_1 \times d_2$$

number of FLOPs (forward pass)

each element in the output matrix $Y$ is computed as a dot product of a length-$d_1$ row of $X$ and a length-$d_1$ column of $W$. a single dot product of two vectors of length $d_1$ requires $d_1$ multiplications and $d_1 - 1$ additions, which counts as $2d_1$ floating-point operations (FLOPs).

matrix multiplication dot product: $Y_{i,j} = \text{Row}_i(X) \cdot \text{Col}_j(W)$ 2$d_1$ ops per output element

since output matrix $Y$ has dimensions $\text{bs} \times d_2$, there are $\text{bs} \times d_2$ individual dot products to compute. multiplying the operations per dot product by the total number of output elements gives:

$$\text{FLOPs} = \text{bs} \times d_2 \times 2d_1 = 2 \times \text{bs} \times d_1 \times d_2$$

note: this is a simple introductory exercise, but we will be using similar calculations throughout to derive parameter counts and FLOPs for the entire transformer model (including attention projections, feed-forward networks, and layer norms).

full transformer model architecture

building upon our linear projection building block, the complete decoder-only transformer architecture stacks multiple identical layers together, transforming token inputs into vocabulary logits.

transformer decoder architecture

core components

  • token & positional embeddings (bottom): converts input token IDs into continuous vectors of dimension $d_{\text{model}}$ and adds positional information.
  • stacked decoder layers (num_layers): multiple identical blocks repeating the sequence:
    • layer norm 1 → self-attention with residual connection 1.
    • layer norm 2 → feed-forward network (FFN) with residual connection 2.
  • language modeling head (top): projects the final hidden states back to vocabulary logits to predict next tokens.

transformer inference: parameter and flop breakdown

below we count the parameters and inference FLOPs of a decoder-only transformer, module by module. inference has two stages:

  • prefill (compute-bound): the whole prompt ($s$ tokens per sequence) is processed in parallel and the kv cache is filled. every weight matrix is read once and reused across $b \times s$ tokens, so arithmetic intensity is high and the large matmuls keep the compute units busy. latency here is the time to first token (ttft).
  • decode (memory-bandwidth-bound): one new token per sequence is generated per step. every step still reads all weights and the whole kv cache, but each weight supports only $b$ tokens (about 2 flops per parameter per sequence), so step time is set by memory bandwidth, not flops. latency here is the time per output token (tpot).

positional embedding (only if not using rope)max_seq $\times d_{\text{model}}$ (learned), 0 (sinusoidal)$b \times s \times d_{\text{model}}$$b \times d_{\text{model}}$

the position lookup is free; only the elementwise add to the token embeddings costs flops, one add per element.

sinusoidal tables are fixed functions of position and dimension, precomputed and cached, so no parameters and no per-pass generation cost. parameters depend on max_seq; flops depend on the sequence length actually run.

in decode, the new token's position index is $s$ (the number of tokens already cached). skip this row entirely when using rope.

output projection (unembedding)$d_{\text{model}} \times V$$2 \times b \times s \times d_{\text{model}} \times V$$2 \times b \times d_{\text{model}} \times V$

a real matmul. tied weights change the parameter count (0 additional) but not the flops.

prefill only needs the last position's logits to sample the next token, so many implementations compute just that one: $2 \times b \times d_{\text{model}} \times V$. the full-$s$ version applies to training, scoring and perplexity.

for large vocabularies this is a big slice of decode cost: the $d_{\text{model}} \times V$ matrix is read in full every step and can be a large fraction of weight traffic in small models. softmax over logits and sampling are excluded (about $b \times V$, negligible).

same per-element count as the final norm (square, accumulate, divide, scale). standard layernorm would cost about 7 flops per element and $2 \times d_{\text{model}}$ parameters, which is why rmsnorm is slightly cheaper.

self-attn: q, k, v projections$3 \times d_{\text{model}} \times nh \times d_{\text{head}}$$6 \times b \times s \times d_{\text{model}} \times nh \times d_{\text{head}}$$6 \times b \times d_{\text{model}} \times nh \times d_{\text{head}}$

three linear layers, each $2 \times bs \times d_1 \times d_2$ with $bs = b \times s$, $d_1 = d_{\text{model}}$, $d_2 = nh \times d_{\text{head}}$.

decode projects only the new token; its k and v are appended to the kv cache and cached tokens are never re-projected.

with gqa/mqa, k and v output width shrinks to $n_{kv} \times d_{\text{head}}$: parameters become $d_{\text{model}} \times d_{\text{head}} \times (nh + 2 n_{kv})$ and prefill flops $2 \times b \times s \times d_{\text{model}} \times d_{\text{head}} \times (nh + 2 n_{kv})$.

decode reads these weights in full every step for only $b$ tokens of work, a major source of its memory-bound behavior.

self-attn: rope on q and k0$6 \times b \times s \times nh \times d_{\text{head}}$$6 \times b \times nh \times d_{\text{head}}$

each pair $(x_1, x_2)$ is rotated by a position-dependent angle: $x_1' = x_1 \cos - x_2 \sin$, $x_2' = x_1 \sin + x_2 \cos$. that is 4 multiplies and 2 adds per pair, or 3 flops per element. applied to q and k only (not v), so $3 \times 2 = 6$ per (token, head, $d_{\text{head}}$) position for mha. with gqa: $3 \times b \times s \times d_{\text{head}} \times (nh + n_{kv})$.

cos/sin tables are precomputed and cached, so no per-pass generation cost.

decode rotates only the new q and k because cached keys were stored already rotated. if an implementation re-rotates the whole cache, decode costs $3 \times b \times nh \times d_{\text{head}}$ (q) $+ 3 \times b \times s_{\text{kv}} \times nh \times d_{\text{head}}$ (k).

self-attn: s = qkᵀ0$2 \times b \times nh \times s^2 \times d_{\text{head}}$$2 \times b \times nh \times s_{\text{kv}} \times d_{\text{head}}$

prefill: per head, $(s \times d_{\text{head}}) @ (d_{\text{head}} \times s)$. the full $s \times s$ matrix is counted; causal masking could in principle halve it but the usual convention ignores that.

decode: one query row against $s_{\text{kv}}$ cached keys, so cost is linear in context instead of quadratic.

decode must read the whole key cache: $b \times s_{\text{kv}} \times n_{kv} \times d_{\text{head}}$ elements per layer. this traffic grows with context and is a second source of memory-boundedness alongside weight reads.

self-attn: softmax0$5 \times b \times nh \times s^2$$4 \times b \times nh \times s_{\text{kv}}$

elementwise over the score matrix, so no $d_{\text{head}}$ factor. prefill's 5 ops per element: scale by $1/\sqrt{d_{\text{head}}}$, causal mask, exp, sum (reduction), divide.

decode needs no mask since the single query may attend to every cached position, leaving 4 ops per element over the $s_{\text{kv}}$ scores per head.

max-subtraction for numerical stability (compare + subtract, 2 more per element) is not counted. many implementations fold $1/\sqrt{d_{\text{head}}}$ into q and fused kernels (flashattention) fuse the mask; counting them keeps the tally conservative. softmax is about $1/d_{\text{head}}$ of the matmul cost, a small correction.

self-attn: o = s·v0$2 \times b \times nh \times s^2 \times d_{\text{head}}$$2 \times b \times nh \times s_{\text{kv}} \times d_{\text{head}}$

same shape and cost as qkᵀ: $(s \times s) @ (s \times d_{\text{head}})$ per head in prefill, one row of weights against $s_{\text{kv}}$ cached values in decode. together the core matmuls total $4 \times b \times nh \times s^2 \times d_{\text{head}}$ (prefill) and $4 \times b \times nh \times s_{\text{kv}} \times d_{\text{head}}$ (decode).

decode also reads the whole value cache, so total kv-cache reads per layer are $2 \times b \times s_{\text{kv}} \times n_{kv} \times d_{\text{head}}$ elements.

with gqa the matmul flops stay the same (queries still use all $nh$ heads), but cache size and traffic shrink by $nh / n_{kv}$.

part 4: how cost scales with length (prefill $l_1$ tokens, decode generating the $l_2$-th token)
time to first token (prefill)n/a$O(l_1 d^2 + l_1^2 d)$n/a

here $d = d_{\text{model}}$ with $b$, $L$, $V$ fixed. the $l_1 d^2$ term comes from the ffn (and the attention projections, which scale the same way) and is linear in $l_1$. the $l_1^2 d$ term comes from self-attention (qkᵀ and s·v); its softmax part is $O(nh \, l_1^2)$.

the output projection adds $O(l_1 d V)$ if logits are computed at every position, or $O(dV)$ for the last position only.

ttft grows roughly linearly with prompt length while $l_1$ is small relative to $d$, then turns quadratic once $l_1$ exceeds about $6d$.

cost per subsequent token (decode)n/an/a$O(d^2 + (l_1 + l_2) d)$

the $d^2$ term (ffn, projections, output projection) is constant because only the new token is processed. the $(l_1 + l_2) d$ term is self-attention over the kv cache, linear in context; its softmax part is $O(nh \, (l_1 + l_2))$.

each new token costs roughly constant at short context, then grows linearly once $l_1 + l_2$ exceeds about $6d$.

cumulative cost of generating $n$ tokens: $O(n d^2 + n \, l_1 d + n^2 d)$, quadratic in generated tokens and linear in prompt length for fixed $n$.

memory traffic: kv-cache reads per step are also $O(l_1 + l_2)$ while weight reads stay constant. at long context the cache reads eventually exceed the weight reads, so step time starts growing with context length.

conclusion: how cost scales with length

  • ttft (prefill, $l_1$ tokens): $O(l_1 d^2 + l_1^2 d)$. roughly linear in prompt length while $l_1$ is small relative to $d$ (ffn and projections dominate), turning quadratic once $l_1$ exceeds about $6d$ (self-attention dominates).
  • tpot (decode, $l_2$-th token): $O(d^2 + (l_1 + l_2) d)$. flat at short context, then linear in context length once $l_1 + l_2$ exceeds about $6d$.
  • when $l_2 \ll l_1$: the context is $l_1 + l_2 \approx l_1$ for every generated token, so tpot is set almost entirely by the prompt, $O(d^2 + l_1 d)$, and stays essentially constant across the generation instead of growing with $l_2$. the cumulative decode cost $O(l_2 d^2 + l_2 \, l_1 d + l_2^2 d)$ loses its $l_2^2 d$ term, leaving $O(l_2 d^2 + l_2 \, l_1 d)$.
  • where the flops go: total request cost is prefill plus $l_2 \times$ tpot. since $l_2 \ll l_1$, prefill carries about $l_1 / l_2$ times the flops of decode (both its $d^2$ and its attention terms), so ttft dominates the flop count.
  • wall-clock caveat: decode is memory-bound, so its time is not proportional to flops. each of the $l_2$ steps still reads all weights plus a kv cache that scales with $l_1$. with a long prompt, tpot rises with $l_1$ even when few tokens are generated, because cache reads eventually exceed weight reads.
  • contrast, $l_2 \gg l_1$: tpot grows with $l_2$ as the cache fills, and the cumulative decode cost becomes quadratic in generated tokens.
